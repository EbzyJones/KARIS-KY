TITLE: [SECURITY] Add Replay Protection for Migrate Calls

SEVERITY: HIGH (when migration logic is implemented)
STATUS: Pre-implementation security gap
COMPONENT: escrow/src/lib.rs::LiquifactEscrow::migrate()
AFFECTED VERSIONS: v7+ (when migration logic is added)

PROBLEM STATEMENT:
─────────────────────────────────────────────────────────────────────────────

The migrate() function will be vulnerable to transaction replay attacks when
migration logic is eventually implemented (e.g., v6 → v7 schema upgrade).

Current state (today):
  • All code paths PANIC before storage writes → NO RISK
  • Auth guard already required by documentation
  • No migration logic exists

Future state (when migration is added):
  • State rewrites could be applied twice if:
    - Transaction is replayed (admin key compromised, retry loops, etc.)
    - Off-chain systems accidentally re-submit migration calls
  • Result: yield calculations duplicated, per-investor records corrupted
  • Audit logs become inconsistent

ROOT CAUSE:
─────────────────────────────────────────────────────────────────────────────

No contract-level idempotency protection exists. While Soroban's host provides
transaction-level replay prevention via auth nonces, the contract lacks explicit
guards to prevent:

  1. Manual re-calls to migrate() by administrators
  2. Replay of migration code if implementation is incomplete
  3. Double-application of state transformations

PROPOSED SOLUTION:
─────────────────────────────────────────────────────────────────────────────

Implement contract-level idempotency protection using migration execution nonce:

  1. Add DataKey::MigrationExecutionLog(from_version, to_version)
  2. Add EscrowError::MigrationAlreadyApplied (code 93)
  3. Before applying migration: check if nonce exists; fail if so
  4. After successful migration: write nonce to prevent re-application

ACCEPTANCE CRITERIA:
─────────────────────────────────────────────────────────────────────────────

✓ AC1: DataKey enum has MigrationExecutionLog(u32, u32) variant
✓ AC2: EscrowError enum has MigrationAlreadyApplied = 93
✓ AC3: migrate() checks for prior execution before applying logic
✓ AC4: Successful migration writes execution nonce
✓ AC5: Error code 93 documented in error reference
✓ AC6: OPERATOR_RUNBOOK.md updated with replay-protection guidance
✓ AC7: 3 unit tests added (idempotency, persistence, version isolation)
✓ AC8: Security checklist §5.1 revised
✓ AC9: Code comments explain idempotency check

All acceptance criteria have detailed specifications and implementation steps
in the full issue document (SECURITY_ISSUE_MIGRATE_REPLAY_PROTECTION.md).

================================================================================
                         SECURITY ANALYSIS
================================================================================

THREAT MODEL:
─────────────────────────────────────────────────────────────────────────────

Attacker: Compromised admin key or accidental transaction replay
Attack Vector: Call migrate() multiple times with the same version pair
Impact: Double-application of state transformations
  • Yield calculations applied twice
  • Per-investor records duplicated
  • Collateral audits skewed
  • Accounting inconsistency

DEFENSE IN DEPTH:
─────────────────────────────────────────────────────────────────────────────

Level 1 (Host): Soroban transaction nonce prevents same signature replay
Level 2 (Contract): Idempotency nonce prevents same version transition replay
        (NEW — this issue)

Both layers work together:
  • Host nonce: "This exact transaction was already executed"
  • Contract nonce: "This version migration was already applied"

MITIGATION COMPLETENESS:
─────────────────────────────────────────────────────────────────────────────

✓ Prevents unintended double-application of migrations
✓ Survives WASM upgrades (stored in instance storage)
✓ Provides clear operator feedback (error code 93)
✓ Enables audit trails (optional timestamp recording)
✓ No breaking changes (backward compatible)
✓ Minimal performance impact (O(1) operations)

OUT OF SCOPE (Handled by Soroban host):
─────────────────────────────────────────────────────────────────────────────

  • Transaction signature validation
  • Authorization ledger entry processing
  • Network-level replay prevention
  • Signer nonce management
