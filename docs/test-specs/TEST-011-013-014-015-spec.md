## #413 — TEST-011: sweep_terminal_dust cap enforcement (MAX_DUST_SWEEP_AMOUNT)

**File:** `escrow/src/tests/settlement.rs`

### Background

`sweep_terminal_dust` is guarded by a hard per-call cap: any `amount` argument
greater than `MAX_DUST_SWEEP_AMOUNT` (= `100_000_000` base units) must be
rejected with the typed error `EscrowError::SweepAmountExceedsMax` (code 32)
before any token transfer is attempted.

Constant (`lib.rs` line 194):
```rust
pub const MAX_DUST_SWEEP_AMOUNT: i128 = 100_000_000;
```

Guard in implementation:
```rust
ensure(
    &env,
    amount <= MAX_DUST_SWEEP_AMOUNT,
    EscrowError::SweepAmountExceedsMax,
);
```

Two existing tests near this area are disabled (`#[ignore]` / `#[cfg(any())]`)
due to token-setup or annotation mismatches. `dos_analysis.rs` only asserts the
constant value; `coverage.rs` maps the error code number but does not run the
enforcement flow. There is **no active test** that routes
`try_sweep_terminal_dust` with `amount > MAX_DUST_SWEEP_AMOUNT` through a
properly settled escrow and asserts typed error code 32.

### Steps to Reproduce / Proposed Solution

Use `setup_funded_with_token` (already in `settlement.rs`) or
`init_and_fund_with_real_token` from `tests.rs` to build a settled escrow
backed by a real SAC. Three test functions are required:

**Case 1 — one-over-cap rejected:**
`try_sweep_terminal_dust(MAX_DUST_SWEEP_AMOUNT + 1)` on a settled escrow →
`ContractError(32)`. State unchanged (no transfer).

**Case 2 — exact cap accepted:**
`sweep_terminal_dust(MAX_DUST_SWEEP_AMOUNT)` on an escrow whose token balance
is `≥ MAX_DUST_SWEEP_AMOUNT` → succeeds, returns exactly `MAX_DUST_SWEEP_AMOUNT`.
Verifies the boundary is `≤`, not `<`.

**Case 3 — zero amount rejected before cap check:**
`try_sweep_terminal_dust(0)` → `ContractError(31)` (`SweepAmountNotPositive`).

### Expected vs Actual Behaviour

| Scenario | Expected | Current gap |
|---|---|---|
| `amount = MAX_DUST_SWEEP_AMOUNT + 1` on settled escrow | `ContractError(32)` | No active test asserts this path |
| `amount = MAX_DUST_SWEEP_AMOUNT` on settled escrow | Returns `MAX_DUST_SWEEP_AMOUNT`, treasury balance increases | No active test covers the exact-boundary happy path |
| `amount = 0` | `ContractError(31)` | Covered in `coverage.rs` map; no isolated test in the settlement module |

### Environment Context

- `MAX_DUST_SWEEP_AMOUNT = 100_000_000` — `lib.rs` line 194
- Errors: `SweepAmountNotPositive = 31`, `SweepAmountExceedsMax = 32`
- Token setup: real SAC required (`setup_funded_with_token` or
  `init_and_fund_with_real_token`); `sweep_terminal_dust` calls `token.transfer`
- Escrow must be status `2` (settled), `3` (withdrawn), `4` (cancelled), or `5`
  for the cap check to be reached
- Auth: `env.mock_all_auths()` sufficient; treasury auth required for the
  actual sweep

### Acceptance Criteria

- [ ] `test_sweep_terminal_dust_cap_one_over_rejected` — `try_sweep_terminal_dust(MAX_DUST_SWEEP_AMOUNT + 1)` on a settled escrow returns `ContractError(32)`; `get_escrow().status` is still `2`.
- [ ] `test_sweep_terminal_dust_cap_exact_boundary_accepted` — `sweep_terminal_dust(MAX_DUST_SWEEP_AMOUNT)` with sufficient balance returns `MAX_DUST_SWEEP_AMOUNT`; treasury token balance increases by that amount.
- [ ] `test_sweep_terminal_dust_zero_amount_rejected` — `try_sweep_terminal_dust(0)` returns `ContractError(31)`.
- [ ] All three tests are active (no `#[ignore]`, no `#[cfg(any())]`), pass under `cargo test`, and use `assert_contract_error` rather than `#[should_panic]`.
- [ ] No existing passing tests are broken.

## #415 — TEST-013: UniqueFunderCount cap enforcement — fund rejected at max

**File:** `escrow/src/tests/funding.rs` (or `cap_validation.rs`)

### Background

`init` accepts `max_unique_investors: Option<u32>`, stored as
`DataKey::MaxUniqueInvestorsCap`. On every `fund` call for a new investor
address (`prev == 0`), the implementation checks:

```rust
ensure(
    &env,
    cur_funder_count < cap,
    EscrowError::UniqueInvestorCapReached,  // code 107
);
```

Existing tests in `cap_validation.rs` and `funding.rs` exercise this path but
use `#[should_panic]` and do not verify post-rejection state invariants:

- `get_unique_funder_count()` is unchanged after rejection
- `get_contribution(inv_rejected)` is `0`
- Escrow `status` is unchanged
- Follow-on deposits from an already-counted investor at cap are not blocked
- `max_unique_investors = Some(0)` is rejected at `init` time

### Steps to Reproduce / Proposed Solution

**Case 1 — cap=1, second new investor rejected, state unchanged:**
Init with `max_unique_investors = Some(1)` and a large target. Fund `inv_a`
→ succeeds. `try_fund(&inv_b, ...)` → `ContractError(107)`. Assert:
`get_unique_funder_count() == 1`, `get_contribution(&inv_b) == 0`,
`status == 0`.

**Case 2 — cap=2, follow-on by existing investor not blocked:**
Init with `max_unique_investors = Some(2)`. Fund `inv_a`, fund `inv_b` (both
succeed, count = 2). Fund `inv_a` again (follow-on) → succeeds.
`try_fund(&inv_c, ...)` → `ContractError(107)`. Assert:
`get_unique_funder_count() == 2`, `get_contribution(&inv_a) == combined`,
`get_contribution(&inv_c) == 0`.

**Case 3 — no cap configured, unlimited investors accepted:**
Init with `max_unique_investors = None`. Fund 5 distinct investors → all
succeed. `get_unique_funder_count() == 5`.

**Case 4 — cap=0 rejected at init:**
`try_init(..., &Some(0u32), ...)` → typed contract error
(`EscrowError::MaxUniqueInvestorsNotPositive`). Ensures the cap value itself
is validated before storage.

### Expected vs Actual Behaviour

| Scenario | Expected | Current gap |
|---|---|---|
| `fund` by new investor at cap | `ContractError(107)` | Covered but only via `#[should_panic]`; no state-invariant assertions |
| `get_unique_funder_count` after rejection | Unchanged | Not explicitly asserted |
| `get_contribution(rejected)` after rejection | `0` | Not explicitly asserted |
| Follow-on by existing investor at cap | Succeeds | Covered in one test; not part of a cohesive state-invariant set |
| `max_unique_investors = Some(0)` at init | Typed init error | Tested via `#[should_panic]` only |

### Environment Context

- `UniqueInvestorCapReached = 107` — `lib.rs` line 356
- `MaxUniqueInvestorsNotPositive` — check exact code via grep on `EscrowError`
- `DataKey::UniqueFunderCount` incremented in `fund_impl` when `prev == 0`
- Target must be large enough that the escrow stays open (status 0) when the
  cap is hit, so the test doesn't conflate cap rejection with
  `EscrowNotOpenForFunding`

### Acceptance Criteria

- [ ] `test_013_cap1_second_investor_rejected_state_unchanged` — `try_fund` on a new address at cap returns `ContractError(107)`; count, status, and rejected-investor contribution unchanged.
- [ ] `test_013_cap2_followon_existing_investor_not_blocked` — follow-on deposit from an already-counted address at cap succeeds; new address is rejected with `ContractError(107)`; count stays at cap.
- [ ] `test_013_no_cap_unlimited_investors` — 5 distinct funders all succeed with `max_unique_investors = None`; `get_unique_funder_count() == 5`.
- [ ] `test_013_cap_zero_rejected_at_init` — `try_init` with `max_unique_investors = Some(0)` returns the expected typed init error.
- [ ] All tests use `assert_contract_error` for error-path assertions; none use `#[should_panic]`.
- [ ] All tests pass under `cargo test -p karis-ky_escrow`.

## #416 — TEST-014: claim_investor_payout — pro-rata accuracy with 3-investor scenario

**File:** `escrow/src/tests/settlement.rs`

### Background

`claim_investor_payout` records a payout claim after settlement. The payout
for investor _i_ is:

```
payout_i = floor(contribution_i × settle_pool / total_principal)
settle_pool = total_principal + floor(total_principal × yield_bps / 10_000)
```

An existing e2e test (`e2e.rs` ~line 257) runs a 3-investor scenario but:

- Does not assert individual amounts against the formula
- Does not verify `is_investor_claimed` flags independently per investor
- Does not test ordering independence (claims in any order)
- Does not verify second-call idempotency precisely
- Uses a `±3` rounding margin on the total that can be tightened

This issue targets a dedicated, formula-precise test set in `settlement.rs`.

### Steps to Reproduce / Proposed Solution

Use `setup_funded_with_token` (already in `settlement.rs`) with
integer-friendly amounts chosen for clean arithmetic.

**Setup:**
- `target = 1_000_000`, `yield_bps = 1_000` (10 %)
- `inv_a` contributes `500_000` (50 %)
- `inv_b` contributes `300_000` (30 %)
- `inv_c` contributes `200_000` (20 %)
- Total principal = `1_000_000`
- Settle pool = `1_100_000`
- Expected payouts: `inv_a = 550_000`, `inv_b = 330_000`, `inv_c = 220_000`
- Sum = `1_100_000` exactly (no rounding residual — deliberately chosen)

**Assertions:**

1. `get_escrow().status == 2` after `settle()`.
2. `compute_investor_payout(&inv_a) == 550_000` (view-only, pre-claim).
3. `claim_investor_payout(&inv_a)` succeeds; `is_investor_claimed(&inv_a) == true`.
4. Second `claim_investor_payout(&inv_a)` is idempotent; flag still `true`.
5. `is_investor_claimed(&inv_b) == false` (unaffected by inv_a's claim).
6. Claims for `inv_b` and `inv_c` each succeed; flags set independently.
7. Payout sum == exact `settle_pool` (= `1_100_000`).
8. Ordering independence: repeat with claim order `inv_c → inv_b → inv_a`;
   individual payout amounts identical.
9. Non-participant: `try_claim_investor_payout(&stranger)` → typed contract
   error.

### Expected vs Actual Behaviour

| Scenario | Expected | Current gap |
|---|---|---|
| Individual payout amounts match formula | Exact match | Not formula-verified in `settlement.rs` |
| `is_investor_claimed` per investor independent | Set only after own claim | Partially covered in `e2e.rs`; not in `settlement.rs` |
| Second claim idempotent | No state change | Mentioned in `e2e.rs`; not formula-checked |
| Ordering independence | Identical amounts | Not tested anywhere |
| Payout sum exact | `== settle_pool` | Only `±3` margin in `e2e.rs` |

### Environment Context

- Formula: `docs/escrow-pro-rata.md` (authoritative)
- `compute_investor_payout` — view-only, no auth required
- `is_investor_claimed` — returns `bool` for a given address
- Real SAC required for `settle()` to succeed (token transfer); use
  `setup_funded_with_token`
- Tests go under a `// ── Pro-rata accuracy ──` section header in
  `settlement.rs`

### Acceptance Criteria

- [ ] `test_014_three_investor_pro_rata_exact_payouts` — individual payout amounts match the floor-division formula exactly; `is_investor_claimed` set per investor after their own claim call only.
- [ ] `test_014_three_investor_claim_idempotent` — second `claim_investor_payout` for the same investor does not panic and does not alter payout or flag.
- [ ] `test_014_three_investor_claim_ordering_independent` — forward and reverse claim orders produce identical `compute_investor_payout` values for all three investors.
- [ ] `test_014_three_investor_payout_sum_exact` — `payout_a + payout_b + payout_c == settle_pool` for the chosen integer amounts.
- [ ] `test_014_non_participant_claim_rejected` — `try_claim_investor_payout(&stranger)` returns a typed contract error.
- [ ] All tests pass under `cargo test -p karis-ky_escrow`; none are `#[ignore]`.

## #417 — TEST-015: record_sme_collateral_commitment — empty field rejections

**File:** `escrow/src/tests/admin.rs`

### Background

`record_sme_collateral_commitment(asset: Symbol, amount: i128)` validates two
inputs before writing:

```rust
ensure(&env, amount > 0, EscrowError::CollateralAmountNotPositive);  // code 60
ensure(
    &env,
    asset != Symbol::new(&env, ""),
    EscrowError::CollateralAssetEmpty,                                // code 61
);
```

Existing tests in `admin.rs`:
- `test_collateral_zero_panics` — `amount = 0`, `#[should_panic]`. No typed
  error or state assertion.
- `test_collateral_requires_sme_auth` — no auth, `#[should_panic]`. Does not
  cover `CollateralAssetEmpty`.

No test currently:
- Passes an empty `Symbol` and asserts `ContractError(61)`
- Uses `assert_contract_error` for either rejection
- Verifies that a rejection leaves `get_sme_collateral_commitment()` unchanged

### Steps to Reproduce / Proposed Solution

All tests use `setup` + inline `init`. Empty symbol: `Symbol::new(&env, "")`.

**Case 1 — zero amount rejected, no prior record:**
`try_record_sme_collateral_commitment(&symbol_short!("USDC"), &0i128)` →
`ContractError(60)`. Assert `get_sme_collateral_commitment().is_none()`.

**Case 2 — empty asset rejected, no prior record:**
`try_record_sme_collateral_commitment(&Symbol::new(&env, ""), &500i128)` →
`ContractError(61)`. Assert `get_sme_collateral_commitment().is_none()`.

**Case 3 — zero amount rejected, prior record preserved:**
Write a valid record first (`amount = 1_000`, `asset = "GOLD"`). Then
`try_record_sme_collateral_commitment(&symbol_short!("GOLD"), &0i128)` →
`ContractError(60)`. Assert prior record intact: `amount == 1_000`.

**Case 4 — empty asset rejected, prior record preserved:**
Same first write, then `try_record_sme_collateral_commitment(&Symbol::new(&env, ""), &999i128)` → `ContractError(61)`. Assert prior record intact.

**Case 5 — valid overwrite succeeds:**
Two sequential valid calls with different amounts and assets; second call's
values are stored. Non-regression: valid updates are not accidentally blocked.

### Expected vs Actual Behaviour

| Scenario | Expected | Current gap |
|---|---|---|
| `amount = 0` | `ContractError(60)` | Tested via `#[should_panic]` only; no state assertion |
| `asset = Symbol::new(&env, "")` | `ContractError(61)` | **No test exists** |
| Rejection preserves prior record | `get_sme_collateral_commitment()` unchanged | Not tested |
| Valid overwrite accepted | New record stored | Not tested in isolation in `admin.rs` |

### Environment Context

- `CollateralAmountNotPositive = 60`, `CollateralAssetEmpty = 61` — `lib.rs`
  lines 297–300
- `get_sme_collateral_commitment()` returns `Option<SmeCollateralCommitment>`
- `SmeCollateralCommitment` fields: `asset: Symbol`, `amount: i128`,
  `recorded_at: u64`
- Empty symbol: `Symbol::new(&env, "")` — use this form; `symbol_short!("")`
  may not compile
- SME auth required; `env.mock_all_auths()` covers it throughout
- `CollateralUpdateAfterSettlement` (code 63) guard is out of scope for this
  issue

### Acceptance Criteria

- [ ] `test_015_collateral_zero_amount_rejected_typed` — `try_record_sme_collateral_commitment` with `amount = 0` returns `ContractError(60)`; storage is unchanged.
- [ ] `test_015_collateral_empty_asset_rejected_typed` — `try_record_sme_collateral_commitment` with `Symbol::new(&env, "")` and positive amount returns `ContractError(61)`; storage is unchanged.
- [ ] `test_015_collateral_zero_amount_preserves_prior_record` — rejection with `amount = 0` after a valid write leaves the prior `SmeCollateralCommitment` intact.
- [ ] `test_015_collateral_empty_asset_preserves_prior_record` — rejection with empty asset after a valid write leaves the prior `SmeCollateralCommitment` intact.
- [ ] `test_015_collateral_valid_overwrite_succeeds` — two sequential valid calls result in the second record being stored.
- [ ] All tests use `assert_contract_error`; none use `#[should_panic]`.
- [ ] All tests pass under `cargo test -p karis-ky_escrow`.
